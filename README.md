# vela-back

API do Scout Vela, o Talent ID da vela olímpica brasileira. Contexto completo do produto e regras no `AGENTS.md` da raiz do workspace.

```
Navegador ──► vela-front (Vercel) ──► vela-back (Render) ──► Postgres (Supabase)
                     │                                             ▲
                     └──── login (Supabase Auth) ──────────────────┘
```

Node 22 (o Render lê `.node-version`), TypeScript, Fastify 5, Zod 4 (validação e contrato OpenAPI), `pg`, `jose`. Testes com Vitest e PGlite (Postgres real em WASM, sem Docker).

## Banco (Supabase)

Dois projetos na organização da instituição (nunca em conta pessoal). A região prevista era São Paulo (`sa-east-1`), mas ela não estava disponível na criação: o projeto de produção está em US East, Ohio (`us-east-2`). A região não muda depois de criado o projeto; mudar exige recriar e migrar os dados.

| Projeto | Plano | Dados |
| --- | --- | --- |
| `scoutvela-homologacao` | gratuito | seed fictício e 4 contas de teste |
| `scoutvela-producao` | gratuito (ver aviso abaixo) | sem seed; primeiro gestor por `gestor:criar` |

O esquema só muda por migration: nada é criado à mão no painel. As senhas do banco ficam no cofre de senhas do time.

> **Produção no plano gratuito (decisão do piloto).** Os riscos ficam assumidos até a CBVela/IBVAR decidir o upgrade, que deve vir antes de entrarem dados reais em volume:
> - sem backup diário nem PITR pelo painel;
> - o projeto pausa após cerca de uma semana sem atividade (reative em Project Settings > General);
> - limites de 500 MB de banco e 1 GB de Storage.
>
> Até o upgrade, o backup é o dump lógico descrito em "Backup e restauração".

### Montar um ambiente

1. **Projeto.** Crie no painel com senha forte gerada e guarde-a no cofre.
2. **Auth** (Authentication):
   - **desligue o cadastro público** (Sign In / Providers > "Allow new users to sign up"); contas são criadas pela CBVela em `POST /usuarios`. Isto é obrigatório: no primeiro login a API amarra o login ao cadastro pelo e-mail do token (`vincularContaPorEmail`), então quem conseguisse criar conta com o e-mail de um cadastro herdaria o papel dele;
   - **mantenha a confirmação de e-mail ligada** ("Confirm email"), pelo mesmo motivo. O token do Supabase traz `user_metadata.email_verified`; a API só faz o vínculo quando o claim vem `true` e recusa (403) quando ele vem `false` ou não vem (auditoria de 25/11/2026, A1). As duas opções acima continuam obrigatórias, como segunda barreira;
   - ative o MFA por TOTP (Multi-Factor) e use `EXIGIR_MFA=true`;
   - ligue **"Secure password change"** (Authentication > Providers > Email): a troca de senha pelo `updateUser` passa a exigir login recente. O modal "Meu perfil" do front troca a senha sem pedir a atual;
   - em URL Configuration, Site URL = domínio do front e redirect permitido `FRONT_URL/redefinir-senha` (convite e redefinição de senha). Em homologação, inclua também o preview da Vercel e `http://localhost:8080/redefinir-senha`;
   - anote se o projeto usa chave JWT nova (JWKS, deixe `SUPABASE_JWT_SECRET` vazio) ou legada (HS256, guarde o segredo).
3. **`.env` local** apontando para o ambiente (`APP_ENV=homologacao` ou `producao`):
   - `DATABASE_URL`: Connect > Session pooler (porta 5432). A conexão direta é só IPv6 e o Render sai por IPv4;
   - `DATABASE_CA_CERT`: certificado em Database > SSL Configuration (TLS obrigatório);
   - `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (chave secreta) e `SUPABASE_ANON_KEY` (chave pública, só para a verificação).
4. **Esquema:** `npm run db:migrate`.
5. **Verificação:** `npm run db:verificar` precisa terminar sem `FALHA`. Ele confere:
   - toda migration da pasta registrada em `schema_migrations`;
   - RLS em toda tabela do schema `public`;
   - bucket `evidencias` privado, 5 MB, só PDF, JPG e PNG (criado pela `0007`);
   - a chave pública, pela API REST (`/rest/v1/<tabela>`), não lê nenhuma tabela nem view.
6. **Dados:**
   - homologação: `npm run db:seed` (recusa `APP_ENV=producao` e recusa rodar duas vezes) e `npm run seed:auth` (4 contas de teste);
   - produção: `npm run gestor:criar -- --email <e-mail> --nome "<nome>"`. Cria o primeiro gestor e envia o convite; ninguém conhece a senha. Recusa se já houver gestor ativo. Os demais usuários entram pelo convite em Contas.
7. **Teste:** `npm run dev` com o front local e abra ranking, ficha e login com as contas de teste.

### Migration nova

1. Crie `migrations/NNNN_descricao.sql` com o próximo número. Nunca edite uma migration já aplicada; corrija com outra.
2. Homologação: o pre-deploy do serviço de homologação no Render roda `db:migrate:prod` a cada deploy da `staging`. Sem o serviço no ar, rode `npm run db:migrate` com o `.env` de homologação. Confira com `npm run db:verificar`.
3. Produção: só depois de validada em homologação, pelo deploy da `main` (mesmo pre-deploy). Confira com `db:verificar`.

### Backup e restauração

- **Produção:** enquanto estiver no plano gratuito, o único backup é o dump lógico abaixo, guardado fora do Supabase. Depois do upgrade, os backups diários e o PITR ficam em Database > Backups. A restauração pelo painel substitui o banco inteiro: combine uma janela e avise os usuários antes.
- **Teste de restauração** (feito uma vez em homologação): gere um dump lógico e restaure num banco descartável:

  ```bash
  pg_dump "$DATABASE_URL" --schema=public --no-owner --format=custom --file=homologacao.dump
  pg_restore --no-owner --dbname="$URL_DESTINO" homologacao.dump
  ```

  Depois rode `npm run db:verificar` contra o destino (migrations e RLS precisam passar; o bucket só existe se o destino for um projeto Supabase) e compare a contagem de linhas de `atletas`, `avaliacoes` e `usuarios`. O dump do schema `public` não leva as contas do Supabase Auth nem os arquivos do Storage.

### MFA no modo local

`npm run dev:local -- --mfa` liga `EXIGIR_MFA`: gestor e IBVAR só passam da tela de verificação depois de cadastrar um app autenticador (leia o QR ou digite o segredo) e informar o código de 6 dígitos. Treinador e atleta não são afetados. O emulador implementa TOTP (RFC 6238, SHA-1, 6 dígitos, 30 s) e aceita o código do passo atual e de um passo para cada lado; o mesmo código não vale duas vezes. Os fatores ficam só em memória e somem quando o modo local reinicia, então o cadastro do app é refeito a cada execução. Sem a flag, o MFA fica desligado.

## Regras que o código garante

- **Cálculo só no servidor:** score, faixa e gates são calculados a cada leitura a partir dos parâmetros do banco (pesos, faixas de peso, regras P3/P7, limites dos gates). Nada é digitado. O teste de paridade confere os 14 atletas contra o protótipo.
- **Série histórica:** notas, medidas, gates, consentimentos e financeiro só aceitam `INSERT`, com trigger no banco. O valor atual é o último lançamento. A única exceção é a anonimização (abaixo), que troca texto livre pelo marcador `[removido na anonimização]` dentro da própria transação.
- **Matriz de acesso no SQL:** treinador só vê os próprios atletas; atleta só a si; IBVAR só quem consentiu, sem detalhe sensível, sem contato e só com o perfil de suporte. Quem não consentiu entra só nos agregados.
- **Nota sugerida pela resposta do atleta** não conta no score até o treinador confirmar.
- **Nota dos resultados (D10, regra provisória P12 `PERF_RESULTADOS`):** `perf_mundial`, `perf_continental` e `perf_nacional` são indicadores calculados (como `cf_peso_kg`): a nota sai dos resultados validados do atleta e nunca é digitada (lançar nota neles dá 400, na gravação e na prévia; a autoavaliação não os aceita). Por nível, vale a **melhor colocação** entre os `edicoes_max` resultados mais recentes (por edição, depois por data); nível sem resultado validado vale `sem_resultado` (0, editável na regra): o indicador sempre tem nota e conta como preenchido, porque a média do pilar (P2) ignora indicador sem nota e, sem isso, um pódio nacional sozinho daria 5 ao pilar de Performance e o atleta ficaria sempre incompleto (escala da reunião: "ou zero, ou 4, ou 5"). Nesse caso a ficha traz `explicacao` "Sem resultado validado no <nível> nas últimas N edições" e `resultado: null`. O tamanho da frota não entra. Valor da regra (jsonb em snake_case, editável em `PUT /parametros`, `regras.PERF_RESULTADOS`, com auditoria de antes e depois): `{ edicoes_max: 4, sem_resultado: 0, niveis: { mundial: [{ate:3,nota:5},{ate:10,nota:4},{ate:25,nota:3},{ate:null,nota:2}], continental: [mesma escala], nacional: [{ate:1,nota:5},{ate:2,nota:4},{ate:3,nota:3},{ate:null,nota:0}] } }`; cada faixa vale até `ate` (inclusive), `ate: null` vale para qualquer colocação e só a última faixa o tem, e colocação pior nunca dá nota maior. **Os valores são provisórios**: vêm do exemplo dito na reunião de 23/11 e esperam as faixas oficiais que o Juan (CBVela) vai enviar. Nível do resultado → indicador: `mundial` → `perf_mundial`; `continental` e `sul_americano` (Sul-Americano e Pan-Americano) → `perf_continental`; `brasileiro` → `perf_nacional` (no nacional, fora do pódio vale 0: "só o pódio conta"); `internacional_aberto`, `estadual` e `regional` ficam registrados e não geram nota. A ficha (`GET /atletas/:id`) traz, no indicador, `origem: "calculado"`, `explicacao` ("Melhor colocação validada no Mundial: 12º em 2026 (Mundial de ILCA 6)") e `resultado: { nivel, posicao, edicao, evento }`. Os pontos do Ranking CBVela continuam importados e aparecem só como informação (`pontosCbvela`); a regra `PERF_PONTOS` e o campo `sugestaoPontos` foram removidos (migration 0030). Não valem como nota: o resultado do atleta pendente ou recusado.
- **Resultados do atleta (D10, migration 0031):** `POST /me/resultados` (só o atleta) informa uma edição de um evento (`evento`, `nivel` mundial|continental|nacional, `ano`, `posicao`, `tamanhoFrota?`, `data?`, `anexoId?` da súmula, `linkOficial?` https; exige a súmula ou o link); nasce `pendente` e avisa o treinador (`atleta_lancou_resultado`). Mais de `edicoes_max` edições do mesmo evento (nome sem diferença de caixa e espaços, mesmo nível) ou edição repetida: 409; recusado não conta. Sem `data`, vale o último dia do ano da edição (hoje, se o ano é o atual), para o resultado entrar nas janelas do G3. `PUT /resultados/:id/validacao` (treinador do atleta ou gestor) grava `validado` ou `recusado` (motivo obrigatório) em `validacoes_resultado`, tabela só de inserção (a situação vigente é a da validação mais recente; sem validação, pendente), e avisa o atleta. `GET /atletas/:id/resultados?status=` lista com fonte, edição, súmula, motivo e quem validou; o IBVAR só recebe os validados, sem anexo, motivo nem quem validou. Contam direto: os lançados por gestor ou treinador (`fonte = 'manual'`) e os importados do Ranking CBVela; os do atleta (`fonte = 'atleta'`) só depois de validados. Os gates G2 e G3 mantêm as regras, mas só enxergam resultados válidos: o Mundial do G2 exige a frota informada (a regra é por fração posição/frota), e o resultado do atleta no nível `continental` conta no G3 mas não no Sul-Americano do G2 (o nome do evento é texto livre). A súmula do atleta (categoria `sumula`) fica ligada ao resultado e não pode ser removida (409). `indicadores.orientacao` (até 1.000 caracteres) é o texto de ajuda de cada indicador, editável em `PUT /parametros` (`indicadores: [{ id, orientacao }]`, `null` remove).
- **Histórico do indicador:** `GET /atletas/:id/indicadores/:indicadorId/historico` lista os lançamentos do mais novo para o mais antigo (valor, evidência, origem, avaliador, ciclo, data e anexo), com a sugestão pendente do atleta marcada (`pendente: true`). `cf_peso_kg` traz as pesagens de `medidas_corporais`. Segue a matriz da ficha; para o IBVAR, pilar sensível dá 403 e os demais vêm sem evidência, avaliador, anexo nem sugestão.
- **Cadastro pelo ID World Sailing (D1):** o ID World Sailing (`atletas.ws_id`) é a chave do atleta: normalizado (maiúsculas, sem espaços), único, obrigatório e no formato `^[A-Z]{3}[A-Z0-9]{2,12}$` (`src/domain/ws-id.ts`; formato inferido de exemplos, ver `docs/world-sailing.md`). O VelaID (`velaid_codigo`) é opcional e continua único quando preenchido.
  - **Gestor cadastra:** `POST /atletas` recebe `wsId`, `email`, `classeId`, `treinadorId`, `confirmaMaioridade: true` (obrigatória) e `velaid` opcional (não exige mais a busca no VelaID; `POST /velaid/busca` segue como atalho). WS ID repetido ou VelaID já usado: 409. Se o `velaid` existir em `velaid_registros`, o vínculo fica guardado e os dados de lá viram sugestão para o atleta; velaid de menor de 18 anos é recusado. Cria a conta e envia o convite e o termo como antes.
  - **Atleta completa:** o atleta nasce com cadastro incompleto (`nome`, `genero` e `data_nascimento` nulos, `cadastro_completo_em` nulo). `GET /me` traz `cadastroPendente: { wsId, velaid, sugestao }` (nulo se já completou; `sugestao` com os dados do VelaID, ou nula sem VelaID) e `PUT /me/cadastro` (só o atleta, uma vez; segunda chamada 409) grava nome, gênero e data de nascimento. Depois disso esses campos só mudam pelo pedido do titular (tipo correção). Os dados sensíveis ficam fora da auditoria.
  - **Trava de 18+:** no `PUT /me/cadastro`, menor de 18 é recusado (400) sem gravar a data, o nome nem o gênero; o atleta e a conta ficam inativos (`cadastro_recusado_em`), abre-se um pedido de exclusão para o gestor anonimizar, a auditoria (`recusar_cadastro_menor`) não guarda data nem idade, e o balão `cadastro` do gestor soma esses casos. `GET /atletas` traz `cadastroRecusado`.
  - **Fora de tudo até completar:** atleta incompleto não entra no ranking, na ficha e no score (404), nas pendências do ciclo, nos lembretes, no fechamento de ciclo (`scores_ciclo`) nem no investimento. O filtro está em `listarAtletasVisiveis`, em `pendenciasDoCiclo` e em `contarSemConsentimentoIbvar` (`cadastroCompletoSql`).
  - **Só o gestor troca o WS ID:** `PUT /atletas/:id` com `wsId` (a auditoria guarda só o nome do campo). O atleta pede correção pelo pedido do titular.
  - **Leitura:** a ficha (`GET /atletas/:id`), `GET /ranking` e `GET /me/perfil` devolvem `wsId`; `velaid` pode ser nulo em todas as respostas. O IBVAR só vê o WS ID de quem consentiu (mesma regra da ficha e do ranking).
  - **Importações:** a do VelaID segue alimentando `velaid_registros`; a do Ranking CBVela acha o atleta pelo código VelaID, então atleta sem VelaID cai como erro de linha e não recebe esses pontos.
- **Lista de gestão:** `GET /atletas` (só o gestor) traz todos os atletas, inclusive inativos, sem termo aceito e com cadastro incompleto (`nome` nulo), com WS ID, classe, treinador, número de vela, situação, termo, `cadastroCompleto`, `cadastroRecusado` e conta vinculada, sem dado sensível nem e-mail. Filtros: `ativo`, `termoAceito`, `cadastroCompleto`, `classeId`, `treinadorId` e `busca` (nome, ID World Sailing ou VelaID).
- **Ciclos:** só um aberto por vez. Ao fechar, a API calcula e congela em `scores_ciclo` o score e a faixa de todos os atletas ativos com termo aceito, numa transação. Ciclo fechado não muda.
- **Financeiro (P8):** o gestor informa o perfil de suporte A–D e os componentes; cada atualização é uma nova linha. Alimenta o G4 e o painel de investimento, não o score.
- **Resultado internacional:** lançado à mão por gestor ou treinador do atleta, com link https do resultado oficial; G2 e G3 são recalculados na leitura.
- **Evolução da turma (D12, migration 0033):** `GET /investimento/evolucao?classeId=` (gestor e IBVAR) traz, por ciclo fechado (mais antigo primeiro), `atletas`, `scoreMedio`, `mediaPorPilar`, `funil` por faixa e `aptosNosGates`, a partir do que o fechamento congelou (ciclo antigo: pilares e gates nulos), e `meta` (dois últimos ciclos fechados contra `META_EVOLUCAO.percentual`, padrão 10). Sigilo: para o IBVAR, ciclo com menos de `MIN_GRUPO_AGREGADO.minimo` atletas (padrão 3) no recorte vem `suprimido: true` com os números nulos; o gestor vê tudo. `GET /investimento` não tem recorte e não aplica o mínimo. Médias com duas casas. Funções puras em `domain/evolucao.ts`.
- **Atleta contra a turma (D13, migration 0034):** `GET /atletas/:id` traz `mediaTurmaPorCiclo` (`{ cicloId, ciclo, media, atletas }` por ciclo fechado, mais antigo primeiro, a média de todo o piloto em `scores_ciclo`), `comparacaoTurma` (`{ scoreAtual, mediaTurma, diferenca, posicao }` do último ciclo fechado com score do atleta; `na_media` se a diferença absoluta for menor que `TENDENCIA.limiar`, padrão 2) e `tendencia` (`subindo`, `estavel` ou `caindo`, pelos dois últimos scores do atleta contra o mesmo limiar; nula com menos de dois). Vale para todo papel que vê a ficha. Para o IBVAR, ciclo com menos de `MIN_GRUPO_AGREGADO.minimo` atletas tem `media` nula e a comparação some. Funções puras em `domain/turma.ts`.
- **Perfil com bio e conquistas (D14, migration 0036):** `atletas.bio` (texto simples, 1 a 500 caracteres) é editada pelo atleta em `PUT /me/perfil` (`bio`; vazio ou `null` apaga; a auditoria guarda só o nome do campo) e volta em `GET /me/perfil` (`atleta.bio`) e na ficha (`atleta.bio`). `conquistas` na ficha lista só as validadas: os pódios (1º a 3º) dos resultados validados (`tipo: resultado`, com `evento`, `nivel`, `posicao`, `ano` = edição; calculados na leitura) e as manuais (`tipo: manual`). Anexo removido de atleta visível responde 410 no link; atleta anonimizado responde 404 em tudo. **D5 (evidência opcional e link):** cada indicador tem `evidencia` (`obrigatoria` ou `opcional`; opcional em `tec_*`, `tat_*` e `pot_*`) e `exige_anexo` (`cf_peso_kg`), editáveis pelo gestor em `PUT /parametros` (`indicadores: [{ id, evidencia }]`). Peso do atleta: `POST /me/pesagens` (foto `balanca`), `PUT /pesagens/:id/validacao` (treinador ou gestor) e `GET /atletas/:id/pesagens`; só o peso validado vira medida (Class Fit e G1) e a foto sai do Storage depois da decisão. **D11 (atleta anexa):** o atleta envia e remove anexos só no próprio cadastro (outro atleta: 404), com `categoria` `evidencia` (padrão), `sumula` ou `balanca`. Cota de 200 MB por atleta (`COTA_ANEXOS_BYTES`, soma dos anexos não removidos): acima dela, 413 `cota_excedida`. O atleta só remove o que ele mesmo enviou e que não esteja ligado a uma nota (409). A listagem traz `categoria`, `enviadoPor.papel`, `usoBytes` e `cotaBytes`, com filtro `?categoria=`. A limpeza diária não apaga o que o atleta enviou nem o que não é `evidencia`.
- **Chat (D16):** três tipos de conversa em `conversas`: `treinador_atleta` (1:1, privada, ligada ao par treinador+atleta), `gestao_atleta` (o atleta com a gestão) e `gestao_treinador` (o treinador com a gestão); as duas últimas são caixa compartilhada de todos os gestores ativos (cada mensagem guarda o autor; `leituras_conversa` dá "não lidas" a cada gestor). Atleta com atleta não existe e o IBVAR leva 403 em todas as rotas. Rotas: `GET /conversas` (`?supervisao=true`, só gestor: as `treinador_atleta` só com metadados), `POST /conversas`, `GET`/`POST /conversas/:id/mensagens` (até 2.000 caracteres, texto puro; 30 mensagens por minuto por usuário, 429), `PUT /conversas/:id/lidas` e `POST /conversas/:id/acesso-supervisao`. Troca de treinador: o par antigo fica só leitura (`encerrada_em`, preenchida por gatilho) e o novo treinador não o lê. Mensagem nova gera o aviso `mensagem_nova` (`referencia: { conversaId }`), no máximo um não lido por conversa e destinatário. O balão `conversas` de `GET /me/notificacoes` soma as não lidas. `GET /meus-dados` inclui `mensagens`. Retenção: `atletas.inativado_em` e `usuarios.inativado_em` (gatilho em `ativo`) alimentam o `job:limpar-conversas`.
- **Avisos (D8):** `avisos` guarda só o fato (tipo, quem, ids na `referencia`), sem nota, peso, texto livre nem nome de arquivo. A auditoria guarda só ids. `GET /me/avisos` (paginado por data: `limite`, `antesDe`, `apenasNaoLidos`), `PUT /me/avisos/:id/lido` (só o dono; de outro, 404) e `PUT /me/avisos/lidos`; o IBVAR não recebe avisos (lista vazia). - **Sugestões (D7):** `POST /sugestoes` só do treinador (gestor, atleta e IBVAR: 403), com `tipo` `class_fit` (exige `classeId` existente e `proposta` `{ pesoMinKg, pesoMedioKg, pesoMaxKg }`, de 0 a 400 kg, min <= médio <= max, as mesmas regras de `PUT /parametros`), `parametro` ou `sistema` (sem classe nem proposta) e `texto` de 1 a 1.000 caracteres; até 10 abertas por autor (409 acima). `GET /sugestoes?status=`: o gestor vê todas e o treinador só as suas, com a `faixaAtual` da classe para comparar. `PUT /sugestoes/:id` (só o gestor): `aprovada` ou `recusada`, com `resposta` obrigatória ao recusar; só sugestão aberta (senão 409). - **Perfil e foto:** `GET /me/perfil` (atleta, treinador e gestor; IBVAR recebe 403) traz nome, e-mail de login, papel, `fotoUrl` e `mfaAtivo` (sessão atual `aal2`); o atleta recebe os dados de cadastro, o aceite do termo e o consentimento do IBVAR, e o treinador a quantidade de atletas. `PUT /me/perfil` edita o nome (treinador e gestor) ou o e-mail de contato (atleta); os dados do VelaID se corrigem pelo pedido do titular, e a auditoria guarda só os nomes dos campos. `POST /me/foto` aceita JPEG ou PNG até 2 MB, com assinatura conferida e sem EXIF, em `fotos/{usuarioId}/{uuid}.ext` no mesmo bucket das evidências, e remove a anterior (se a remoção falhar, o caminho vai para `arquivos_pendentes`); `DELETE /me/foto` apaga o arquivo e só depois zera o caminho, e responde 204, mesmo sem foto (503 se o Storage falhar: a foto continua e dá para repetir). `GET /me`, a ficha (`GET /atletas/:id`) e os itens de `GET /ranking` (usados também na busca de atletas) trazem `fotoUrl` em link assinado de 5 minutos; na ficha e no ranking, nulo para o IBVAR.
- **Contas e termo:** o gestor cria contas e o Supabase envia o convite. O termo é versionado em `termos_consentimento` (o vigente é o de maior `vigente_desde` que já começou) e o atleta aceita no app; o gestor ainda pode registrar aceite recebido fora dele. `GET /termos` lista as versões com a contagem de aceites e `POST /termos` publica uma nova, com vigência futura e posterior à de todas as outras (o texto não vai para a auditoria). **Aceite antecipado:** o atleta (`POST /termo/aceite`) e o gestor (`POST /atletas/:id/termo`) podem aceitar a versão vigente ou a próxima já publicada, a de menor `vigente_desde` no futuro (`GET /termo/proxima`, só atleta e gestor, com o texto; `GET /termo` segue devolvendo a vigente). Quem aceitou uma versão mais nova que a vigente conta como tendo aceito a vigente, salvo revogação (`concedido = false`) depois do aceite, então com `TERMO_EXIGE_REACEITE` ativa ele continua no ranking quando a nova versão entra em vigor. `GET /painel` traz `termoProxima` (`{ versao, titulo, vigenteDesde }`, ou nulo) com a próxima versão que o atleta ainda não aceitou. `POST /ciclos/:id/fechar` recusa com 409 quando nenhum atleta tem o termo aceito mas há atletas ativos (nada a congelar). A única saída sem anonimizar é a recusa formal, `{ resposta, recusar: true }`, com justificativa de ao menos 20 caracteres, auditada como `recusar_exclusao`. `GET /pedidos-titular` traz, no pedido de exclusão que anonimizou o atleta, `anonimizacao: { em, pendencias: { arquivos, conta } }` (nulo nos demais), calculado pelo estado do banco (`arquivos_pendentes`, foto ainda registrada, `anonimizacoes_pendentes`); falha só de listagem do Storage aparece na resposta da própria anonimização, não neste campo.

O acesso é aplicado no SQL e o front consulta a cada 60 s. `PUT /me/notificacoes/vistas` com `{ chave }` grava o instante da visita (tabela `notificacoes_vistas`) e responde 204; por enquanto só o atleta marca `painel` (outros casos: 400). Dado de interface, sem auditoria.
- **Auditoria:** toda escrita grava quem, quando, ação e ids, sem valores sensíveis. O gestor consulta em `GET /auditoria`.
- **RLS ativo em todas as tabelas, sem política:** a chave pública do Supabase não lê nada. A API conecta com a credencial de servidor, que fica só no Render. Há teste que confere RLS em toda tabela nova.

## Segurança

- **Requisições:** JWT validado em toda requisição (issuer, audience, expiração), CORS só para os domínios do front, Helmet (CSP `default-src 'none'`, HSTS), limite de 300 requisições por minuto por IP e corpo de até 1 MB. O envio de evidências (`POST /atletas/:id/evidencias`, corpo de até 8 MB) tem limite próprio de 20 por minuto por usuário autenticado, além do limite por IP (429 `limite_excedido`); o da foto de perfil (`POST /me/foto`, corpo de até 3 MB), de 10 por minuto. Nessas duas rotas a sessão e o limite por IP são conferidos no `onRequest`, antes de o corpo ser lido: sem token válido a resposta é 401 sem consumir o corpo.
- **IP do cliente (`TRUST_PROXY_HOPS`):** o limite por IP usa o IP que o Fastify enxerga. `TRUST_PROXY_HOPS` é quantos proxies confiáveis ficam na frente da API (o `X-Forwarded-For` é lido da direita para a esquerda, só nesses saltos). Padrão: 0 em desenvolvimento e 1 em homologação e produção (no Render é 1). Não aumente sem saber: valor alto demais deixa o cliente forjar o IP e burlar o limite.
- **IBVAR e o peso:** o motivo do gate G1 normalmente traz a diferença em kg da média da classe, o que revelaria o peso. Para o IBVAR a ficha devolve um texto sem número ("Dentro da faixa da classe", "Leve desvio da faixa da classe", "Fora da faixa da classe") e anula também o texto de `evidencia` dos indicadores (como o histórico já fazia).
- **Logs e erros:** logs estruturados (pino) sem token, cookie nem corpo, e todo 401/403 vira log `acesso_negado`. Os erros seguem o formato `{ erro, mensagem }`, e o 500 não expõe detalhe interno.
- **CSRF:** não se aplica. O token vai no header `Authorization`, não em cookie.
- **Dependências:** CI com typecheck, lint, formatação, testes, build, contrato OpenAPI e `npm audit --omit=dev`. Dependabot semanal.
- **LGPD:** não guarda CPF, documento, endereço completo nem renda; a importação de CSV recusa essas colunas. O consentimento é registrado com histórico, e o atleta pode pedir revisão de nota (art. 20). O treinador responde os pedidos dos próprios atletas (1ª instância) e o gestor responde qualquer um em `PUT /revisoes/:id` (outro treinador: 404), podendo ligar a resposta ao lançamento que a atendeu (`avaliacaoId`); `GET /revisoes` mostra `notaAnterior` e `notaNova`, e o atleta recebe um e-mail só com o aviso e o link. Se o atleta discorda da resposta do **treinador**, `POST /revisoes/:id/recurso` (uma vez, até 1.000 caracteres) reabre o pedido na 2ª instância (`instancia = 2`), só para o gestor, e a resposta dele encerra. A 1ª resposta é copiada para `resposta_1`, `respondido_por_1` e `respondido_em_1` e o recurso fica em `recurso_texto` e `recurso_em` (migration 0023); pedido respondido pelo gestor não tem recurso.

## Pendências que dependem da CBVela ou do controlador dos dados

- **Regra de pendência do atleta:** hoje conta as perguntas do questionário nunca respondidas, sem olhar o ciclo (`repositories/pendencias.ts`). A CBVela precisa dizer se a pendência é por ciclo (resposta a cada rodada) ou não.
- **`cf_altura_cm`:** o indicador ainda pontua no Class Fit, embora já exista a faixa de altura da classe (só informativa). A CBVela decide se a altura passa a ser só informativa e o indicador sai do score.
- **Faixas de altura:** os valores reais por classe e função estão em branco; precisam vir da CBVela (`alturaMinCm`, `alturaMediaCm`, `alturaMaxCm` em `PUT /parametros`).
- **Faixas de colocação (`PERF_RESULTADOS`):** os valores são provisórios (exemplo da reunião de 23/11) até o Juan, da CBVela, enviar as faixas oficiais por nível e o número de edições. Os pontos do Ranking CBVela ficam só como informação.
- **Controlador dos dados:** CBVela ou IBVAR, a definir. Quem for precisa validar o que a anonimização apaga e o que mantém (série histórica sem texto livre, data de nascimento generalizada, regata sem link, auditoria sem nome nem VelaID).
- **Revogação do termo:** hoje só acontece na anonimização. Falta definir se o atleta pode revogar sem ser anonimizado (e o que acontece com o histórico).
- **Confirmação de e-mail no Supabase:** ligar "Confirm email" no projeto de homologação e de produção. O vínculo de conta por e-mail só vale com o e-mail confirmado no token.

## Deploy (Render)

O `render.yaml` (Blueprint) descreve o web service e o Cron Job dos lembretes.

- **Web service:** build `npm ci && npm run build`, start `npm start`, pre-deploy `npm run db:migrate:prod`, health check `/health`.
- **Cron Job dos lembretes:** `npm run job:lembretes:prod`, todo dia às 11:00 UTC (08:00 de Brasília).
- **Cron Job da limpeza de anexos:** `npm run job:limpar-anexos:prod`, todo dia às 06:00 UTC (03:00 de Brasília); precisa das variáveis do banco e do Storage.
- **Cron Job da limpeza de avisos:** `npm run job:limpar-avisos:prod`, todo dia às 06:30 UTC (03:30 de Brasília); só precisa das variáveis do banco.
- **Cron Job da retenção do chat (D16):** `npm run job:limpar-conversas:prod`, todo dia às 06:45 UTC (03:45 de Brasília); só precisa das variáveis do banco.
- **Variáveis:** `APP_ENV`, `TRUST_PROXY_HOPS` (opcional; padrão 1 fora do desenvolvimento), `DATABASE_URL`, `DATABASE_CA_CERT`, `SUPABASE_URL`, `SUPABASE_JWT_SECRET` (só se for chave legada), `SUPABASE_SERVICE_ROLE_KEY`, `CORS_ORIGINS`, `FRONT_URL`, `EXIGIR_MFA=true`, `EMAIL_PROVEDOR=smtp`, `EMAIL_REMETENTE`, `SMTP_*` e `STORAGE_PROVEDOR=supabase`. Fora do desenvolvimento a API recusa subir com Storage local ou SMTP sem host.
- **Ambientes:** homologação e produção são serviços separados, cada um com seu projeto Supabase. Produção usa instância paga, porque o plano gratuito hiberna.
